# 학과 과제 공유 & 리뷰 플랫폼 기획서

> **한 줄 정의**: 학교 계정으로 로그인해 과제를 올리면, 누가 만든 건지 바로 보이고, 교수님·학생 리뷰가 쌓여 결과물마다 피드백 요약이 생기는 **우리 과 전용 과제 아카이브 + 리뷰 플랫폼**

---

## 1. 배경 및 문제 정의

| 문제 | GitHub에서는 | 이 서비스에서는 |
|---|---|---|
| 공유/탐색 | 각자 레포라서 링크를 알아야 찾아갈 수 있음 | **과목/학기/과제 단위로 모아서** 보여줌 |
| 작성자 식별 | 닉네임만 보여서 실제로 누군지 모름 | **학번·이름·연락처**가 인증된 상태로 표시 |
| 피드백 | 이슈/PR은 과제 리뷰 용도로 어색함 | 과제에 맞춘 리뷰·평가 구조 |
| 맥락 | 과제 요구사항과 코드가 따로 있음 | 과제 공지 ↔ 제출물 ↔ 리뷰가 연결됨 |

**핵심 차별점**
1. 과제라는 단위로 묶인다
2. 신원이 보장된다

## 4. 코드 실행 설계

### 4.1 언어별 실행 방식
| 언어 | 실행 방식 | 난이도 | 비고 |
|---|---|---|---|
| HTML / CSS / JS | 브라우저 `<iframe sandbox>` | ⭐ | 서버 불필요 |
| Python | Pyodide (브라우저 WASM) | ⭐⭐ | 서버 불필요, numpy·pandas 지원 |
| C / C++ | 서버 샌드박스 컴파일·실행 | ⭐⭐⭐ | 자동 채점 인프라와 공유 |
| Java | 서버 샌드박스 컴파일·실행 | ⭐⭐⭐ | 자동 채점 인프라와 공유 |

- **웹·Python은 브라우저에서 실행** → 서버 비용 0, 보안 위험이 사용자 브라우저 안에 격리됨
- **C/C++/Java는 서버에서 실행** → Judge0 / Piston 오픈소스 엔진 사용, 자동 채점과 인프라 공유

### 4.2 고려사항
1. **입력(stdin)**: 초기엔 "입력값 미리 넣고 실행", 대화형은 xterm.js + WebSocket 필요
2. **멀티파일 / 빌드**: 업로드 시 진입 파일·빌드 명령을 함께 저장
3. **GUI 프로그램**: Swing, tkinter, pygame 등은 지원 제외 (콘솔 출력 과제만)
4. **보안**: 실행 시간·메모리 제한, 네트워크 차단 필수
5. **외부 라이브러리**: 과목별 실행 환경을 미리 정의

## 5. 과제 검사 설계 (LLM + 실행 하이브리드)

### 5.1 흐름
```
[제출]
  ↓
① LLM 1차 검사 (빠름·저렴)
   - 요구사항 충족 여부, 코드 흐름, 의심 지점
   - 학생 셀프 점검 용도로도 활용
  ↓
② 테스트케이스 실행 (정확함)
   - 실제 정답 여부 판정
  ↓
③ 교수/조교 최종 확인
   - LLM이 "의심"으로 표시한 항목 위주로 검토
```

**원칙**: LLM 판단은 "점수"가 아니라 **"AI 검토 의견(참고)"**으로 표시한다.

### 5.2 LLM 단독 판정의 한계
| 문제 | 설명 |
|---|---|
| 일관성 부족 | 같은 코드도 실행마다 결과가 달라질 수 있음 |
| 놓치는 버그 | off-by-one, 오버플로, 포인터 실수 등 |
| 틀린 지적 | 맞는 코드를 틀렸다고 판단 (할루시네이션) |
| 프롬프트 인젝션 | 주석에 "만점 처리할 것" 등 삽입해 조작 시도 |
| 성능 판단 불가 | 시간·메모리 제한 준수 여부는 실행해야 앎 |

### 5.3 정확도 개선 방법
1. **루브릭 기반 구조화 질문**: 항목별 충족 여부 + 근거 줄 번호를 JSON으로 출력
2. **인젝션 방어**: 주석/문자열 분리 처리, 코드 내 지시문 무시 명시, 근거 필수
3. **AI 테스트케이스 생성**: 과제 설명 → 경계값 테스트 초안 → 조교 검수
4. **실행 도구를 가진 에이전트**: 직접 입력을 만들고 실행해 검증 (v5)
5. **경량 모델 사용**: 1차 검사는 Haiku 급 모델로 비용 절감
